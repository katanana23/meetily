# Политика веток и обновлений форка

Форк: `katanana23/meetily` («Aid Meetings»).
Оригинал: [`Zackriya-Solutions/meeting-minutes`](https://github.com/Zackriya-Solutions/meeting-minutes) (Meetily), лицензия MIT.

## 1. Ветки

| Ветка | Назначение | Кто пишет |
|---|---|---|
| `main` | Зеркало `main` оригинала. Своих коммитов нет. Обновляется только быстрой перемоткой (`--ff-only`) из `upstream/main` | никто, кроме синхронизации |
| `aid` | Рабочая ветка форка: патч идентичности, документация, свои изменения. Отсюда собираются сборки «Aid Meetings» | все изменения форка |
| `feature/*`, `fix/*`, `claude/*` | Короткие ветки от `aid`, вливаются в `aid` через pull request | разработчик или агент |

Правила:

- В `main` не коммитить и не делать в неё pull request. Если в `main` попал свой коммит, синхронизация через `--ff-only` перестанет работать.
- Все pull request форка направлены в `aid`, не в `main`.
- Обновления оригинала попадают в `aid` только слиянием (`merge`), без `rebase`: история `aid` опубликована, переписывать её нельзя.

## 2. Как подтянуть обновления оригинала

Один раз в клоне:

```bash
git remote add upstream https://github.com/Zackriya-Solutions/meeting-minutes.git
git remote -v   # origin = katanana23/meetily, upstream = оригинал
```

Каждое обновление:

```bash
# 1. Обновить зеркало main
git fetch upstream --tags
git checkout main
git merge --ff-only upstream/main
git push origin main

# 2. Влить main в aid через отдельную ветку
git checkout aid
git pull --ff-only origin aid
git checkout -b sync/upstream-$(date +%Y%m%d)
git merge --no-ff main -m "merge: upstream $(git describe --tags --always main)"

# 3. Проверить патч идентичности (раздел 3), собрать, проверить
# 4. Отправить и открыть pull request sync/... -> aid
git push -u origin HEAD
```

Если `git merge --ff-only upstream/main` в шаге 1 падает, значит в `main` форка есть свои коммиты. Их надо перенести в `aid` и вернуть `main` к `upstream/main` (это переписывание `main`, делать вручную и осознанно).

Слияние лучше делать по релизным тегам оригинала (`git merge v0.4.2`), а не по каждому коммиту `main`: так видно, на какой версии оригинала стоит форк.

## 3. Как не потерять патч идентичности

Патч идентичности это один коммит «chore(fork): isolate app identity». Полный перечень правок с файлами и строками: [`docs/isolation.md`, раздел 4](isolation.md#4-перечень-правок-патча-идентичности).

При слиянии оригинал меняет те же файлы (`tauri.conf.json` почти в каждом релизе меняет `version`). Конфликт или тихая потеря правки возможны в трёх случаях:

1. **Конфликт в соседних строках.** Например, оригинал поднял `version` в строке 4 `tauri.conf.json`, а форк менял строки 3 и 5. Разрешать так: версия от оригинала, `productName`, `identifier`, `title` и блок `plugins.updater` от форка.
2. **Оригинал добавил новое место с зашитым «Meetily».** Конфликта не будет, но появится новая утечка. Например, новый `.join("Meetily")` или новое уведомление с заголовком `"Meetily"`.
3. **Оригинал переписал файл целиком** (переименование модуля). Тогда замена константой пропадёт без конфликта.

Проверка после каждого слияния (из корня репозитория):

```bash
# Идентичность в конфиге
grep -nE '"(productName|identifier|title|createUpdaterArtifacts|pubkey|endpoints)"' frontend/src-tauri/tauri.conf.json
# Ожидается: Aid Meetings, io.github.katanana23.aid-meetings, false, "", []

# Константы на месте
grep -n 'fork_app_name\|APP_DISPLAY_NAME\|APP_DATA_DIR_NAME\|RECORDINGS_DIR_NAME' frontend/src-tauri/src/config.rs

# Новые зашитые имена оригинала в путях и заголовках ядра
grep -rnE '(join|push)\("[Mm]eetily|meetily-recordings|"Meetily( Error)?"|com\.meetily\.ai' \
  frontend/src-tauri/src --include=*.rs | grep -v lib_old_complex.rs
# Ожидается только запасной путь моделей (whisper_engine.rs, parakeet_engine.rs, model_manager.rs),
# см. docs/isolation.md, раздел 2

# Новые плагины, которые зависят от идентичности
grep -nE 'tauri-plugin-(deep-link|autostart)' frontend/src-tauri/Cargo.toml
grep -n 'plugins' -A20 frontend/src-tauri/tauri.conf.json
```

Если что-то из этого вывело неожиданное, поправить в том же pull request слияния отдельным коммитом `chore(fork): reapply identity after upstream vX.Y.Z`.

Если оригинал добавил плагин `deep-link` (схема `meetily://`) или `autostart`, их надо развести так же: своя схема, своё имя элемента автозапуска. Пополнить таблицу в `docs/isolation.md`.

Если оригинал добавил миграцию базы, она применится к базе форка при первом запуске. Это нормально, база у форка своя. Но свои миграции форк добавлять не должен без крайней необходимости: при следующем слиянии номера и содержимое могут разойтись с оригиналом.

## 4. Правило для правок ядра

Ядро это всё, что не интерфейс: `frontend/src-tauri/**` (Rust, `tauri.conf.json`, `Cargo.toml`, миграции), сборочные скрипты, `.github/workflows`.

- Правки ядра делаются **только по необходимости**: то, что нельзя сделать в интерфейсе, конфиге или документации.
- Каждая правка ядра это **отдельный коммит** с префиксом `chore(fork):` или `fix(core):` и описанием «зачем». В одном коммите не смешивать ядро и интерфейс.
- Каждая правка ядра заносится в `docs/isolation.md` (или отдельный список правок ядра) с файлом и строкой.
- Чем меньше правок ядра, тем дешевле каждое слияние оригинала. Если исправление полезно оригиналу, лучше предложить его в оригинал pull request-ом и дождаться релиза.

## 5. Опция: merge-драйвер «ours» для путей интерфейса (не включена)

Идея: если интерфейс форка будет полностью переписан, изменения оригинала в `frontend/src/**` при слиянии можно автоматически отбрасывать в пользу версии форка.

Как включается (сейчас **не включено**, файла `.gitattributes` с этими строками нет):

```gitattributes
# .gitattributes
frontend/src/** merge=ours
frontend/public/** merge=ours
```

```bash
# Драйвер настраивается в каждом клоне отдельно, в репозиторий это не попадает
git config merge.ours.driver true
```

Как работает: при трёхстороннем слиянии файла, который изменили обе стороны, git вызывает драйвер. Драйвер `true` ничего не делает и сообщает об успехе, поэтому в результате остаётся версия текущей ветки (`aid`).

Плюсы:

- Слияния оригинала проходят без конфликтов в интерфейсе.
- Редизайн форка не затирается правками оригинала в тех же компонентах.

Минусы:

- Драйвер срабатывает **только для файлов, изменённых обеими сторонами**. Если оригинал изменил файл, который форк не трогал, изменение оригинала всё равно придёт. Новые файлы оригинала тоже придут. В итоге интерфейс может оказаться смесью.
- Изменения оригинала отбрасываются **молча**, без конфликта и без следа в выводе `git merge`. Исправления ошибок и безопасности в интерфейсе пропадут, и никто этого не заметит.
- Интерфейс зависит от ядра: если оригинал переименовал команду Tauri или событие и поправил вызов в интерфейсе, форк получит новое ядро и старый вызов. Сборка пройдёт, а функция сломается во время работы.
- Настройка `git config merge.ours.driver true` нужна в каждом клоне и в CI. Без неё строка в `.gitattributes` ссылается на неизвестный драйвер, и git сливает файл обычным способом. Поведение зависит от машины.
- GitHub при слиянии pull request на своей стороне пользовательские драйверы не применяет, поэтому слияние оригинала надо делать локально.

Вывод: включать стоит только когда интерфейс форка окончательно отделится от оригинала, и вместе с регулярным просмотром `git diff <прошлый тег>..<новый тег> -- frontend/src` оригинала, чтобы вручную переносить нужные исправления.
